# 外呼模块：准备与部署

本模块默认关闭。当前没有配置或创建任何 RDS。代码交付不代表数据库联调、线上容量或生产启用已完成。

## 存储与边界

- 旧客户/订单仍使用原 `data/db.json`；资源、号码密文、跟进、流转、导入批次保存于独立 MySQL 8.0 InnoDB 库。
- 每人私海最多 500 条；管理员分配也受上限约束。已关联客户占一个名额，转客户不会多占名额。
- 正式客户只能由管理员调整所属，并同步资源负责人。销售只能退回未关联正式客户的资源。
- 财务及未知角色无外呼权限。公海不返回完整号码、姓名、地址、客户关联或跟进；来源/地区/标签含数字时隐藏，避免自由文本泄露号码。
- 资源详情允许当前负责人查看以前销售的跟进与关联客户订单摘要，不放宽原订单/客户 API，不返回成本利润，不提供全量号码导出。
- 国内手机号和带区号座机为首期输入范围。其他格式进入失败行，不修改旧手机号归一化规则。
- 标签首期使用受限长度逗号列表，容量固定 500；未启用自动回收、第三方呼叫、录音、外部营销、导出或自动化任务。

## 需要由部署人员准备

1. 确认轻量服务器地域及与 RDS 的连接路径，不假设内网默认互通。应用库与测试库分开。
2. 确认 MySQL 8.0、数据库名称、地址、端口及 TLS CA。应用账号只授予专用库所需 SELECT/INSERT/UPDATE；建表使用独立迁移账号，应用不需要 DROP/DELETE/GRANT。
3. 使用两把不同的随机 32 字节密钥（64位十六进制）：AES-256-GCM 加密密钥与 HMAC-SHA256 索引密钥。密钥通过受限环境文件交给 systemd，不放 Git、聊天、URL、数据库或日志。备份密钥；丢失后无法恢复号码。当前格式 v1，不支持直接替换密钥，轮换必须单独迁移。
4. 配置数据库自动备份；备份恢复要同时核对 JSON 客户及 MySQL 客户关联。应用启动不会自动建表、补建客户资源或修改库。

环境变量（这里只列名称，不填写真实值）：

| 变量 | 含义 |
|---|---|
| LEADS_ENABLED | 0 默认关闭；1 显示管理员准备入口 |
| LEADS_ACTIVE | 0 只准备；1 接管客户资源同步并开放外呼 |
| LEADS_MYSQL_HOST / LEADS_MYSQL_PORT | 数据库地址 / 默认3306 |
| LEADS_MYSQL_DATABASE | 独立外呼库名 |
| LEADS_MYSQL_USER / LEADS_MYSQL_PASSWORD | 专用运行账号 |
| LEADS_MYSQL_CA | CA 文件路径，启用证书校验 |
| LEADS_ALLOW_PRIVATE_PLAINTEXT | 仅经部署人员确认可信私网后才可设1，否则必须提供CA |
| LEADS_ENCRYPTION_KEY / LEADS_INDEX_KEY | 两把不同的密钥 |

## 安装与验证顺序

1. 在测试环境运行根目录 `npm test`。测试脚本在临时副本执行旧测试，保留原商品目录供已有AI回归使用，不在工作区运行 server.js 初始化逻辑；副本测试结束清理。
2. 外呼驱动独立安装：`npm ci --prefix leads --ignore-scripts --legacy-peer-deps`（npm 6 可省略 `--legacy-peer-deps`）。保留根项目依赖不变。`mysql2` 锁定 3.14.5，传递依赖由 `leads/package-lock.json` 锁定。不能只依据包声明升级驱动：较新版本的传递依赖可能使用旧Node不支持的API，升级必须实测。
3. 在专用空测试库验证：名称必须以 `_leads_test` 结尾，配置测试连接变量，设 `LEADS_TEST_CONFIRM=EMPTY_SYNTHETIC_TEST_ONLY`，执行 `node scripts/test-leads-mysql.js`。脚本拒绝非空库，不创建数据库，只在明确提供的空测试库建表并写合成数据，完成后保留测试表供检查。
4. 首次压测可同时设 `LEADS_TEST_ROWS=50000`，覆盖5万条与10并发分页；同时观察应用RSS、CPU、旧开单延迟及RDS慢查询。测试结果出来前不承诺2GB机器容量。其他筛选、深分页及长时间混合负载仍需实测。
5. MySQL验收应覆盖：多人争抢一条、499条时并发领取、重复请求、批量回滚、财务/跨销售访问、导入重复/中断继续、正式客户同步失败恢复和订单摘要权限。

## 生产准备与现有客户迁移（必须独立审阅后执行）

1. 由用户备份并确认现有数据，在维护窗口暂停客户编辑；只运行一个应用进程。旧 JSON 仍不支持多进程写入。
2. 迁移账号在已确认的空外呼库执行 `leads/schema.sql`。此文件包含 CREATE TABLE，没有清库、DROP 或旧业务导入覆盖。
3. 设置 `LEADS_ENABLED=1`、`LEADS_ACTIVE=0`，配置连接和密钥，重启现有 `building-sales-system.service`。
4. 管理员打开外呼管理，读取 `/api/leads/setup` 核对报告。重复号码、无效号码、不适合的负责人、超过500条，必须人工决定；代码不自动删除、转移或回收客户。
5. 确认报告无冲突后，在管理员页面点击初始化按钮，或使用同源管理员会话 POST `/api/leads/setup`，JSON 为 `{"confirm":"MIGRATE_EXISTING_CUSTOMERS"}`。只在 MySQL 补建关联资源，原客户文件不写入。非空资源库拒绝重复初始化。
6. 保持客户写入暂停，设置 `LEADS_ACTIVE=1` 并重启，验证本人客户全部出现在私海、权限及旧开单后再恢复使用。
7. 激活后客户新增、编辑、归属修改和删除均走同步流程。删除正式客户只解除资源关联，保留号码、历史及原负责人，不删除资源。原订单快照保留逻辑仍复用。

## 同步中断、停用与回滚

- MySQL事务先保存加密的客户操作意图，再在旧JSON写入队列落盘，最后标记完成。存在 pending 时拒绝后续外呼读写和客户修改，避免继续扩大不一致；其他旧业务仍可工作。
- 管理员“恢复待完成的客户同步”调用 POST `/api/leads/recover`，重放已记录的操作，不重新生成客户ID。处理重复客户冲突前不能强行改状态。
- 客户指纹用于检测绕过同步的客户修改；停用模块期间修改旧客户后，不能直接再次启用。需要专门核对修复关联，不应手工改指纹绕过检查。
- 首次尚未激活时，关闭两个开关即可回退。已有外呼客户修改之后，先完成 pending 操作，备份并核对两套数据，再停用。不得直接用旧JSON备份覆盖当前数据。
- MySQL连不上时不回退JSON保存外呼资源；激活后的客户修改会明确失败，旧订单读取、开单仍使用原逻辑。

## 导入与数据口径

- 单文件5MB、5000行、60列；XLSX解压上限20MB，在独立192MB堆子进程解析并设置30秒超时。支持选择工作表；CSV支持UTF-8/GB18030。公式号码、科学计数法文本及无效号码提示失败。
- 上传后选择映射、预览计数及失败行，再确认执行。每个入库事务最多100条，页面依次提交；关闭页面会停止后续批次，已提交行保留，可从批次继续。不是常驻后台导入任务。
- 文件内/资源库/已有客户重复均跳过，不修改原归属。每次提交重新核对；数据库唯一键提供最终保护。
- 导入原始内容与映射数据加密保存在批次行，不把上传文件放本地磁盘。失败行修改后重新上传，成功行会识别为重复。批次、幂等记录的保留与归档期限需管理员后续确认，目前不自动删除。
- 接通量来自销售手工跟进；点击tel不代表真实拨打。关联成交复用旧客户有效销售单口径，不含退货，不作为销售业绩重新分配。
- “拒绝联系”仅表示本次电话沟通结果，保留在资源详情的跟进历史中，不建立名单，也不限制后续拨号、领取、分配、客户关联或联系任务。号码来源、授权、录音告知保留未知状态，不自动宣称合法或已获得授权。

## 当前待外部条件完成的验收

RDS网络/TLS/账号、真实MySQL集成测试、5万条混合负载压测、实际手机拨号行为、现有客户迁移报告与生产启用。没有这些结果前，只能作为默认关闭的代码发布。

本次代码验证：完整旧业务及新增测试在 Node.js 26 和 12.22.12 的临时副本通过；锁定的 mysql2 3.14.5 在 Node.js 12.22.12 可加载（未连接数据库）。浏览器使用合成接口数据验证了 1440、375、320 像素下公海掩码、私海详情、电话入口、导入映射和统计渲染，无横向溢出。这些不替代真实数据库与真实手机验收。
